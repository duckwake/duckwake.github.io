<section class="dw-section-block">
<p class="dw-kicker">How it works</p>
<h2 class="dw-h2">From topic to table in one transaction</h2>
<p class="dw-sub">A worker reads new events, computes only what changed, and commits the view's rows, its state and the offsets it read together. Nothing in between can lose or repeat a row.</p>

<div class="dw-arch">
  <div class="dw-arch-col">
    <p class="dw-arch-title">In</p>
    <div class="dw-arch-box"><strong>Kafka topics</strong><span>JSON events, with SASL and TLS</span></div>
    <div class="dw-arch-box"><strong>Lake tables and views</strong><span>read through their change feed</span></div>
  </div>
  <div class="dw-arch-arrow" aria-hidden="true"></div>
  <div class="dw-arch-col dw-arch-core">
    <p class="dw-arch-title">DuckWake worker</p>
    <div class="dw-arch-steps">
      <div><b>1</b>Read<span>the next batch of events</span></div>
      <div><b>2</b>Stage<span>only what changed, as an incremental circuit</span></div>
      <div><b>3</b>Commit<span>rows, state and offsets in one DuckLake transaction</span></div>
    </div>
  </div>

<p class="dw-kicker">Author</p>
<h2 class="dw-h2">SQL you already know, or a dbt model</h2>
<p>A view is a <code>SELECT</code> with windows, joins to lake tables and aggregates. Create it with one call, or keep it as a dbt model next to the rest of your project: <code>dbt run</code> creates and starts it, and leaves it alone until its settings or query change.</p>
<p><a href="/docs/reference/sql/">SQL functions</a> · <a href="/docs/guides/dbt/">dbt-duckwake</a></p>
</div>
<div class="dw-feature-visual">
<Tabs syncKey="authoring">
<TabItem label="SQL">

```sql
CALL duckwake_create_view('analytics.clicks_per_min',
  'SELECT window_start, game_id, count(*) AS n,
          sum(amount) AS revenue
   FROM TUMBLE(clicks, ts, INTERVAL 1 MINUTE)
   GROUP BY ALL');
CALL duckwake_start('clicks_per_min');
```

</TabItem>

<section class="dw-feature dw-feature-flip">
<div class="dw-feature-text">
<p class="dw-kicker">Trust</p>
<h2 class="dw-h2">Exactly once, and you can check it</h2>
<p>Every epoch is one DuckLake transaction, so after a crash the worker resumes from the last commit and computes the same epoch again. <code>duckwake_verify</code> runs the view's SQL as one batch query over everything it has read and compares it with the view's table.</p>
<p>Every test suite ends with that check, including the ones that kill workers in the middle of a commit.</p>
</div>
<div class="dw-feature-visual">

```sql
FROM duckwake_verify('clicks_per_min');
-- VERIFY OK: clicks_per_min output matches batch recomputation
--            over all 90003 events (epoch 43)
```

</div>
</section>

<section class="dw-feature">
<div class="dw-feature-text">
<p class="dw-kicker">Compose</p>
<h2 class="dw-h2">Views over views, and over your lake</h2>
<p>A view can read another view's table, or any DuckLake table, through its change feed. It starts from the rows already there, then follows inserts, updates and deletes, so filters, <code>DISTINCT</code> and <code>GROUP BY</code> stay correct as the data changes.</p>
<p><a href="/docs/start/concepts/">Concepts</a></p>
</div>
<div class="dw-feature-visual">

```sql
-- Hourly totals from the per-minute view, kept up to date
SELECT game_id, time_bucket(INTERVAL 1 HOUR, window_start) AS hour,
       sum(revenue) AS revenue
FROM analytics.clicks_per_min
GROUP BY ALL
```

</div>

<section class="dw-section-block">
<p class="dw-kicker">Operate</p>
<h2 class="dw-h2">Built to run unattended</h2>
<div class="dw-grid">
  <div class="dw-tile"><h3>Failover and rebalancing</h3><p>Workers heartbeat into the lake. A dead worker's views move to live ones; a new worker takes a share by measured load.</p></div>
  <div class="dw-tile"><h3>Change while running</h3><p>Alter a view's settings in place, replace its query, or add a column to a source, without stopping the rest.</p></div>
  <div class="dw-tile"><h3>Limits that fail small</h3><p>Per-view limits stop one view, not its worker. A worker short of memory shrinks its epochs instead of failing.</p></div>
  <div class="dw-tile"><h3>Metrics and alerts</h3><p>Prometheus metrics, tested alert rules and a Grafana dashboard, each alert with what to do when it fires.</p></div>
  <div class="dw-tile"><h3>Late and bad events kept</h3><p>Events for closed windows go to a late-data table, messages that do not decode to a dead-letter table.</p></div>
  <div class="dw-tile"><h3>Credentials stay out</h3><p>Kafka passwords come from the environment or a file on each worker; nothing secret is stored in the lake.</p></div>
</div>
</section>

<section class="dw-section-block">
<p class="dw-kicker">Compared</p>
<h2 class="dw-h2">Between a cron job and a streaming cluster</h2>

| | A batch job on a schedule | A streaming cluster | DuckWake |
| --- | --- | --- | --- |
| **Freshness** | the schedule: minutes to hours | seconds | seconds: an epoch every few seconds |
| **After a failure** | a half-done run can drop or repeat rows unless the job is idempotent | exactly once, with coordinated checkpoints | exactly once: one DuckLake transaction per epoch |
| **What you run** | a scheduler and a warehouse | a cluster, a state backend, checkpoint storage | workers next to DuckDB, with a PostgreSQL catalog |
| **How you write it** | SQL | SQL or a Java or Python API | SQL, or dbt models |
| **Where results go** | warehouse tables | sinks into other systems | DuckLake tables any DuckDB client reads |
| **Scale** | the warehouse's | many nodes, very high throughput | one machine per worker, views spread across workers |

</section>

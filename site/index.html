Proof of concept · v0.1.0 · built on DuckDB 2.0 and DuckLake 1.1

Continuous SQL over Kafka into DuckLake, exactly once.

You write a view in SQL; DuckWake keeps a DuckLake table up to date with it as events arrive. No streaming cluster: one worker next to DuckDB, and the result is an ordinary lake table.

Quick start How it works

A view in, a fresh table out

Register a Kafka topic as a source, create a view over it, and start it. DuckWake runs the view in micro-batches (epochs) and commits each one to the DuckLake table named after the view. Any DuckDB client can read it.

-- clicks per game, per minute, kept fresh from Kafka
CALL duckwake_create_view('analytics.clicks_per_min',
  'SELECT window_start, game_id, count(*) AS n,
          sum(amount) AS revenue
   FROM TUMBLE(clicks, ts, INTERVAL 1 MINUTE)
   GROUP BY ALL');
CALL duckwake_start('clicks_per_min');

-- an ordinary DuckLake table
FROM lake.analytics.clicks_per_min;

How exactly-once works

Every epoch is one DuckLake transaction. It holds the view's new rows, the view's state and the Kafka offsets it read, so they commit together or not at all.

  1. 1

    Read

    Take the next batch of events from Kafka and decode them (JSON, Arrow decoder by default).

  2. 2

    Stage

    Compute only what changed: the view runs as an incremental operator circuit in the DBSP model.

  3. 3

    Commit

    Write rows, state and offsets in one transaction. After a crash the worker resumes from the last commit.

A crash never loses or duplicates output. duckwake_verify(view) checks a view against the same SQL run as one batch query, and every test in the repository does the same.

What a view can do today

  • Filter and project

    Plain WHERE and SELECT over a Kafka source.

  • Join lake tables

    Lookup joins from the stream to DuckLake tables.

  • Windows

    Tumbling and hopping windows with TUMBLE and HOP, closed by the watermark.

  • Aggregates

    count, sum, avg, min, max, windowed or as running totals per group.

  • DISTINCT and UNION ALL

    SELECT DISTINCT, and UNION ALL across several sources.

  • Late and bad events

    Late events and undecodable messages go to their own tables instead of disappearing.

The operators also accept sources that delete and update rows, ready for CDC; no such source exists yet.

Three ways to run it

duckwakedA server: a worker plus the duckwake_* SQL functions, served over Quack, with Prometheus metrics. Also a Docker image.
LOAD duckwakeThe extension, in your own DuckDB 2.0: the same functions and a worker in that process.
duckwakeA CLI with a command per function, and a playground web UI.

Quick start

The repository is not public yet; this is how it runs once it is. You need Docker (for PostgreSQL, the lake's catalog, and Redpanda, the Kafka) and Rust.

docker compose up -d --wait
cargo build --release          # the first build compiles DuckDB (~6 min)
target/release/duckwaked --worker w1 --quack-token secret

Then, in the DuckDB 2.0 CLI:

ATTACH 'quack:localhost:9494' AS dw (TOKEN 'secret');
CONNECT dw;
CALL duckwake_create_source('clicks', 'kafka', '{"brokers":"localhost:19092","topic":"clicks",
  "event_time":"ts","columns":{"ts":"TIMESTAMP","game_id":"VARCHAR","amount":"DECIMAL(18,2)"}}');
CALL duckwake_create_view('analytics.clicks_per_min',
  'SELECT window_start, game_id, count(*) AS n, sum(amount) AS revenue
   FROM TUMBLE(clicks, ts, INTERVAL 1 MINUTE) GROUP BY ALL');
CALL duckwake_start('clicks_per_min');
FROM duckwake_jobs();                 -- epoch, watermark, freshness, lag
FROM lake.analytics.clicks_per_min;  -- an ordinary DuckLake table

target/release/duckwake produce --rate 2000 sends test events to the clicks topic. The full reference of the duckwake_* functions will be published with the source code.

Status

A proof of concept. Kafka with JSON only. Not yet: CREATE CONTINUOUS VIEW DDL, a signed extension, and stream–stream joins.

  1. P1 · Safety net. CI runs the unit tests and the integration suites on every push.
  2. P2 · A real environment. Automatic failover, Kafka SASL and TLS, object storage, secrets.
  3. P3 · Load and failure. A 24 h soak, failure drills, upgrades and sizing.
  4. P4 · Operable. Runbook, alerts and dashboard, schema changes, limits, distribution.

Each stage ends at a gate that must pass before the next one starts. The source code and the full plan will be published when the repository opens.
